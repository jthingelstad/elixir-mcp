# The migrate ops

Every payload key `services/migrate/src/lambda.mjs` dispatches, one row
each. `services/migrate/test/ops-catalogue.test.mjs` compares the two and
fails `npm run verify` when a dispatched op has no row here, or a row names
an op the dispatcher no longer has. How to run an op, and the rules for
doing it on production, are in `SKILL.md` beside this file.

**The convention the test parses.** An op's row starts with its name in
braces, in backticks: `` | `{stats}` | ``. Nothing else in this file
starts a table row that way.

**The columns.**

- **Payload** is JSON to paste into the invoke. `true` means the op takes
  no arguments; otherwise the keys shown are the ones the op reads, with
  its defaults where they matter.
- **Does** says Read, or **WRITE** and exactly what it writes. A write op
  on production needs its owner's authority, named in the row: an
  objective runbook that grants it, or Jamie. **Heavy** means the op scans
  a large table or the whole corpus on a db.t4g.small: run it once, and
  expect `elixir-mcp-migrate-duration` if it passes 90 s.
- **Named by** is the runbook, skill, doc or script that already uses the
  op. "none" means only the source and the dated notes know it.

**Only `{}` runs the migrations.** That is the call `deploy.mjs` makes. A
payload whose key the dispatcher does not know, a misspelt op name or a
falsy value such as `{"stats": false}`, is refused with `"error":
"unknown_op"` and runs nothing (since 2026-09-25; before, it fell through
to the migration runner and applied anything pending). Copy the key from
this file and pass `true` or an object.

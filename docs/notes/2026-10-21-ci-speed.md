## The Clan flake on main

CI run 39538492981 failed on main with "window is not defined": Clan's
copy-link button (`Actions.jsx`) set state from a bare 1.5 s `setTimeout`
that outlived the test file's jsdom. Eight copy buttons in Clan and the

(`packages/ui/src/flash.ts`), which clears its timer on unmount and
restarts on a second flash; `packages/ui/test/flash.test.tsx` pins both
and scans the view sources so the bare pattern cannot come back.
Playwright now fails CI on a flaky journey (`failOnFlakyTests` under
`CI`); the one retry stays, for its trace. The journey the plan named
(`clan.spec.ts`, then line 1011) was made deterministic by 6d251f1b on
2026-10-20: 40 repeats green here, and the full journeys 356 passed, 0

## One test runner

`npm test` is `infra/scripts/test.mjs`. It builds once (the package
build, or the merged site tree when the `site` unit runs), then runs every
workspace's tests as a bounded pool (half the cores, 2 to 6), holding each
unit's output and printing it whole, then a summary by duration. CI runs
the same runner as `--shard 1/3`, `2/3`, `3/3`: units are spread longest
first onto the lightest shard by `WEIGHTS`, their measured CI seconds, so
a shard's contents change only when a weight or a unit does. A unit runs
as `npm test --ignore-scripts -w <workspace>`, so a workspace's own
`pretest` build (kept for a focused `npm test -w`) never runs while
another workspace reads its output.

Concurrency was safe by construction for databases (each scratch
database is named for its process) and ports (port 0), and the first full
concurrent run found one real race, not in the tests:

**The query budget could outlive its call.** When a budgeted tool's
deadline fired while the invoker's first settings read was still in
flight, the restore found nothing recorded and did nothing; the abandoned
tool then set `lock_timeout`, `work_mem` and a `statement_timeout` of its
remaining milliseconds on the connection, which the next caller on that
Lambda inherited (`query-budget.test.mjs`: `'149ms' !== '1s'`; it passed
alone, every time). Now the setup is one promise per call, recorded
before it sets anything, and sets nothing once the call has been
answered; the restore closes the budget first, waits for a setup in
flight, then puts back what it recorded. A new test makes the slow read
certain (it failed with `statement_timeout: '99ms'` before the fix).

## CI, side by side

`validate.yml` was one serial verify job plus two e2e shards (median 282 s
over the last green runs). Now:

- `static`: the workflow lint, the audits, `npm run verify:static`
  (format, lint, knip, typecheck) and the Lambda bundles.
- `test (1/3)` to `(3/3)`: the runner's shards, each with its own
  Postgres.
- `e2e (1/3)` to `(3/3)`: the journeys, when `changes` says they are
  needed (always on main). Chromium is cached on Playwright's version
  (about 9 s of download); its system libraries install every time. Each
  shard builds the tree once (`build-site.mjs` runs the package build).
- `validate` needs all of them and checks each result, e2e `skipped` only
  when `changes` said false. It stays the one required check and the name
  `ci-gate.mjs` reads.

Every setup-node reads `.node-version` with the npm cache. Locally,
`npm run verify` is `verify:static`, the runner and `build.mjs`: the three
parts CI runs, so nothing runs twice in CI and nothing CI runs is missing
locally.

## e2e-needed.sh told the truth only by luck

The old list answered `false` for 27 files the journeys import or open:
`infra/scripts/build.mjs` (native-ssr bundles with its router alias), 12
`packages/auth` and 8 `packages/mail` files, the relay's
`templates.mjs`, four `services/web-api` files and the quickstart page a
journey opens. It now names them, and `services/mcp/test/ci-tooling.test.mjs`
derives the list instead of trusting it: it bundles every spec (and every
entry a spec bundles) with esbuild, and each repository file in that
closure, and each doc page a spec opens, must answer `true`. The same test
pins the runner's shards (every unit exactly once, deterministic,
balanced) and the workflow's shape.

## Node 24, pinned without engine-strict

`.node-version` says 24; CI's setup-node reads it, `engines.node` is
`24.x`, and Lambda runs `nodejs24.x`. `engine-strict` is not set:
`scripts/worktree-setup.sh` runs in its own shell and cannot put
`node@24` first on the caller's PATH, so strict engines would fail
`npm ci` in every session on this Mac's default Node 26. Instead the
runner prints a banner at its start and end on any other major ("A pass
here is not a pass on 24", with the PATH line), and npm's own engine
warning stays.

## Skipped: a template database

Measured here: a migrated scratch database takes about 1.4 s (229
migrations, warm), a clone from a template 0.4 to 0.8 s, so about 1 s a
database. But databases are made in 73 places across the test files, each
with its own helper, and moving them to one shared template is a
cross-cutting edit while five other sessions work in those packages; and
the test shards are not CI's longest leg, so it would not move
`validate`'s wall time. Not done.

# Web push: the bell on your phone

Jamie, 2026-11-16: "overall the app doesn't have enough to bring people
back" and "should we be sending push notifications via the web?" The
activity mail (`2026-11-16-reach-you.md`, #1071) is the bell's first
channel away from the app; this is the second. Same source: only what the
bell already tells a person, counts never who.

## What a person sees

- **Settings › Notifications** (`/settings/notifications`): this device
  (turn on, or "On for this device" with "Turn off here"), what comes (a
  switch per kind), and the account's devices, each with Remove.
  Permission is asked only inside the tap on "Turn on notifications",
  never on load.
- **iPhone and iPad in Safari** (not on the Home Screen): web push works
  only from a Home Screen app (iOS 16.4+), so the page shows the Share,
  Add to Home Screen steps instead of the button. A blocked browser says
  how to allow it; a browser with no push says so.
- **The bell** carries one quiet line, "Get notified when people cheer
  your play.", with Turn on (a link to Settings, which asks) and Not now,
  which puts it away for good on that device (`localStorage`, wrapped so
  a refusing store only brings the line back). Never shown on a device
  already on, blocked or unable, or when push is off.
- **Kinds:** cheers on your play ("3 cheers on your play", the item's own
  line when it is one item, never who), new followers ("2 new followers",
  "On <your player>", never who), Clan Actions that became yours ("2 Clan
  Actions are waiting for you", from Clan's morning run beside its mail),
  answers to your feedback.
- **Tap** opens the item (the battle, the player, the Clan's Actions, the
  answer) in an open Elixir window or a new one, and marks the notice
  opened.

## How it works

- **Service worker** `apps/web/public/sw.js`, scope `/`: `push` and
  `notificationclick` only. No fetch handler and no cache, so the app
  shell, SSR, sign-in, `/mcp` and the OAuth doors behave exactly as
  before; it registers only from the Turn on tap. It shows text, never
  HTML, with control, direction and zero-width characters taken out and
  lengths capped (120 and 200), and opens only a same-origin path.
  Served by the site bucket as `text/javascript` with the revalidate
  cache rule; `build-site.mjs` requires it. CSP `script-src 'self'`
  already covers it.
- **Schema 0283:** `push_subscription` (one row per device: endpoint,
  keys, a short label; the endpoint is a capability URL, so private
  account machinery: never in a read, only the relay and the account's
  own write see it), `account_push_pref` (a row only for a switch moved;
  no row is on) and `push_notice` (one row per notice, never per device:
  kind, title, body, a path, `through`, `opened_at`, and while it is
  `sending` the devices whose relay object is not yet written,
  `pending`). All cascade with
  the account, and `account-remove` deletes them explicitly.
- **Routes** (`services/web-api/src/routes/push.mjs`), people only (an
  agent is 403, and no agent console route reaches them): `GET
  /api/me/push` (offered, the public key, devices without endpoints,
  kinds), `POST /api/me/push/subscriptions` (endpoint must be `https` on a
  known push service host: FCM, Mozilla, Apple, Windows; 10 devices),
  `DELETE /api/me/push/subscriptions/<id>`, `POST /api/me/push/off`,
  `POST /api/me/push/this-device` (the browser posts its endpoint and gets
  a yes or no back, never an endpoint),
  `PUT /api/me/push/kinds`, `POST /api/me/push/opened`. Writes need the
  `x-elixir-client` contract header. With no key nothing is offered and
  adding a device is 404.
- **Drain** (`services/jobs/src/push/drain.mjs`), each minute on the
  existing minute rule, only with `WebPush` on: people with a device and
  something new (a cheer on their items, a follower, an owed notice, an
  answer), at most one notice an account a run. Order: an owed Clan
  Action, then answers, then cheers (once the latest cheer has settled
  two minutes, so a burst is one notice), then followers. A notice covers
  from the latest of a day ago, the bell's seen marker, the first device
  and that kind's last notice. Caps: ten minutes between notices, eight a
  day. A switched-off kind is skipped; an owed notice held past twelve
  hours is dropped as stale. Agents are never candidates.
- **Sending is the relay's.** The drain writes one `web-push/` outbox
  object per device; the relay (the one function with internet) encrypts
  (RFC 8291 aes128gcm, `node:crypto`), signs VAPID (ES256, 12 hours) and
  POSTs with a 6-hour TTL. It reads the VAPID pair from the
  `elixir-mcp/web-push` secret at runtime and keeps it in memory; the
  private key is in no environment variable. Each result goes back as a
  `push-receipt/` object to timeline-sync: sent stamps the device; 404 or
  410 deletes it.
- **A notice is sent once every device's object is written** (Codex on
  #1077). The drain stores it as `sending` with the devices still owed in
  `pending`, removes each device as its object lands, and marks it `sent`
  when none is left. A failed S3 write, or a run stopped mid loop, leaves
  it `sending`; the next run writes the rest first (same `notice_id`),
  and one still owed after twelve hours is closed. A kind switched off
  meanwhile stops it: nothing more is written (sent if some devices were
  told, dropped if none). A `sending` notice
  counts toward the gap and the daily cap, so a retry never adds a
  second notice. The worst case is one device written twice (its write
  landed, the `pending` update did not); the notification's tag shows it
  once.
- **This device belongs to the account signed in now** (Codex on
  #1077). Settings and the bell's prompt call this device "on" only when
  the browser holds a subscription and `this-device` says it is this
  account's; otherwise the tap saves the browser's subscription again (so
  Remove in Your devices, then Turn on, works). An endpoint held by
  another account is dropped by that answer: holding the endpoint is the
  proof of the browser. **Sign out** turns this browser off first (the
  device row goes and the browser unsubscribes), so the account's notices
  stop here. **Account switch without Sign out** (an expired session,
  then someone else signs in): the shell asks `this-device` once a page
  load when the browser holds a subscription, so the first page the new
  account opens drops the old account's device and its notices stop. A
  notice already handed to the push service before that keeps its
  six-hour TTL; nothing new is queued for that device.
- **The activity mail skips what a tap told:** an opened cheers or
  followers notice moves that part's start to the notice's `through`.
- **Off switch:** stack parameter `WebPush` (`on` by default, classed in
  `parameters.mjs`): off, the API offers nothing, the drain's rule target
  is gone and nothing is sent.

## Infrastructure

- **IAM (inside the stack deploy):** `secretsmanager:GetSecretValue` on
  `elixir-mcp/web-push-??????` only, for the relay's role; S3 object
  grants for the new lanes (jobs writes `web-push/`, the relay reads
  `web-push/` and writes `push-receipt/`, timeline-sync reads
  `push-receipt/`). No KMS grant: the secret uses the AWS managed key.
- **Network:** the relay POSTs to the browsers' push services. No VPC
  change; the VPC Lambdas still reach only S3.
- **Secret:** the web API's `VAPID_PUBLIC_KEY` is a dynamic reference to
  the public half; the private half is read only by the relay at run
  time. Rotation is for a leak only (`docs/SECRETS.md`).
- **CloudFront:** none. `/sw.js` is a site document.

## Product questions, with the default taken

- **Which kinds, default on?** All four, on once a device is on: turning
  a device on is the opt-in. [engineering, from the brief]
- **How often?** At most one notice each ten minutes and eight a day; a
  busy evening is a few pushes. [engineering]
- **Followers named?** Never, though the bell names them: counts, never
  who. [from the brief]
- **Cheers on one item** show that item's own line (already the bell's
  words about the person's own player); several show a count of items.
  [engineering]
- **The bell prompt** shows for anyone not on and able, once per device
  until dismissed. [engineering]
- **iOS outside the Home Screen** gets the steps, not a button that
  cannot work. [from the brief]

## Verification

`npm run verify`; the drain, routes, relay, receipts, account removal and
app tests use fakes at wire precision and per-run keys. Nothing was sent
live; the first real push is a person turning it on after the deploy.

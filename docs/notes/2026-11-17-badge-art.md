# Badge art (2026-11-17)

The owner, 2026-11-17: "Yes use badge art. For sure. In general we were
filtering a lot of things that now a timeline would get value from."

## What the API gives

Every badge on a profile carries `iconUrls.large`, a PNG on
`api-assets.clashroyale.com/playerbadges/512/<opaque id>.png`. The
reference (cr-agent-api-docs `models/players.md`, PR #30) records that it
is one image per badge and tier: 251 (name, level) pairs across the
captured profiles, 251 distinct URLs, none shared. A badge with no tiers
has no `level`.

Until now ingest dropped the field (payload-keys: dropped). It is now
`badge_art.icon_url`.

## Stored

`badge_art` (0288): one row per (name, level), level 0 for a badge with
no tiers, with the icon URL, when it was first seen and when it last
changed. Profile ingest (`projectPlayerBadges`, after the badge upsert)
writes it from every read, the first one included: art is reference, not
news, so silent-first does not apply to it. Only URLs on the API's badge
host and shape are kept; anything else is no art at all. A row whose URL
is unchanged is not rewritten.

## Mirrored, never hotlinked, never altered

`infra/scripts/mirror-card-art.mjs` now mirrors badges after cards, in the
same deploy step:

- the list is the live `GET /api/public/badges`;
- each file is named by the icon URL's own opaque id
  (`/assets/badges/<id>.png`, contracts' `badgeArtPath`), so two rows naming
  one image are one file;
- the id changes when the image does, so a file already held is that image
  and is not fetched again (cards re-fetch every deploy; badges need not);
- it seeds from the bucket's `assets/badges` first, so a fresh worktree
  ships the whole mirror and the 14-day prune never takes a file;
- a fetched file must be a PNG by type and signature, and is written and
  read back byte for byte, exactly as card art is;
- a failure warns and ships what the bucket held. The deploy that first
  ships the route reads it after the stack is up, so the first run already
  answers; if it does not, the next deploy fills it.

The site build passes `src/assets/badges` through when it exists (it is
gitignored, a cache like the card art), and `scripts/worktree-setup.sh`
clones it into new worktrees.

## Shown

Home's feed adds `badge_art` (a path on Elixir's origin) to:

- a single `badge_earned` moment: the icon of the level it tells;
- `legendary_badge_earned`: level 0;
- `twelve_win_run` when the run raised the badge's level.

A Mastery roll-up (a day's Mastery levels as one item) keeps its card art.
A 12-win run that raised no level names no level, so it draws none rather
than guess one.

The web draws it in the moment's art slot and in a small moment's line,
sized by CSS width alone (56px and 24px, height auto). No background,
border, radius, filter or overlay. When the file has not been mirrored yet
(a level first seen since the last deploy) the image fails and the moment
draws what it drew before: the card for a Mastery badge, else the medal.

## The disclaimer

Coverage is the same as card art's: every app page carries the Fan Content
disclaimer in its shell, the site's pages in their footer, and
`/api/public/badges` carries `disclaimer` like `/api/public/cards`. MCP,
RSS, Discord and mail do not carry badge art.

## When art appears

A badge level gets its row the first time Elixir reads a profile that
holds it (profiles are read once a day, every 8 hours for a player someone
follows directly), and its file at the next deploy after that. So after
this ships: rows fill within a day for the badges recorded players hold;
the feed shows art from the deploy after that. A moment from before a
level's row exists gains art once it does, since the feed looks it up when
the page is read.
